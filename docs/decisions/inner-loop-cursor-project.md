# インナーループを Cursor Project に寄せる

**状態:** 採用（2026-10-12）  
**関連:** [#47](https://github.com/yamkazu/yohaku/issues/47)

## 決定

インナーループは Cursor Project「Yohaku」に切り替える。

- アウターループ（朝のルーティン）は、issue ごとに個別のクラウドエージェントを起動しない。issue をこの Project に渡す。
- Project のコーディネーターが作業を分け、スレッドに渡す。
- マージの判断はこれまでどおり人が行う。エージェントはマージしない。

## 理由

以前の形では、依存は issue 本文の「依存」でしか表せず、並行して出したエージェント同士の衝突を防げなかった。

例として [#42](https://github.com/yamkazu/yohaku/issues/42) と [#43](https://github.com/yamkazu/yohaku/issues/43) が同時に動き、どちらも `scripts/verify.sh` と `scripts/ci/run.sh` を触った。

Cursor Project のコーディネーター方式なら、依存のある作業を実行順に並べ、同じファイルを触る作業を直列にできる。

## 役割の分担

| 役割 | やること |
|---|---|
| アウターループ | issue とラベルをそろえ、この Project に渡す。個別エージェントは起動しない |
| インナーループ（本 Project） | 渡された issue を実装し、未マージの PR を出す。`npm run verify` を通す |
| 人 | マージの採否。テーブル削除、権限変更、デプロイ方法の変更など `needs-human` の作業 |

## 見直し条件

次のどれかが続くときは、この決定を見直す。

- コーディネーターが依存順や衝突回避を十分にできず、同じファイルを触る PR が再び並行して衝突する
- GitHub からどのスレッドが何をしたかを追えず、検証や巻き戻しのコストが個別エージェント方式より明らかに高い
- コストや待ち時間が許容できず、小さな独立 issue をアウターループから直接出した方が速いことが繰り返される

切り戻す場合も、マージの判断は人が行う前提は変えない。
